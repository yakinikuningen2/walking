# 長距離の徒歩ルート（2026-11-15）

## 原因

通常は `https://valhalla1.openstreetmap.de/route` の `pedestrian`、予備はPythonの `/api/walking-routes` からopenrouteserviceの `foot-walking` を使います。今回の公開Valhalla稼働版は3.9.2-a919bb6でした。

- 公開Valhallaで距離上限が発生します。約99kmの入力は距離検査を通過（海上の検査座標なので、その後`NoSegment`）、約101kmはHTTP400 `DistanceExceeded`。約100kmの**入力座標間距離**の制限と整合します。徒歩の道のりの長さとは別です。実際、東京〜熱海は道のり104.2kmを取得できました。
- アプリは距離にかかわらず通常18秒で取得を打ち切り、`DistanceExceeded`/154以外の長距離失敗では予備APIを試さず、同じ全区間を追加の種類でも検索していました。
- このPCの試験環境には `ORS_API_KEY` がありませんでした。従来は通常検索の上限を超えると、予備もキー未設定で終了します。キー値の取得・表示・保存はしていません。
- HTTPステータス／APIコードと描画失敗の区別が不十分でした。今回の実例は、地図の描画容量ではなくAPI取得側の失敗でした。104km・3,845点、157km・4,281点のLeaflet描画を確認しています。
- 手動案内には元々散歩時間による拒否はなく、その仕様を維持します。条件検索・ランダム・周遊は別の処理で、時間・速度・実経路による制限を維持します。

## APIの仕様と確認範囲

| API | 距離・地点数 | タイムアウト・留意事項 |
| --- | --- | --- |
| FOSSGIS Valhalla | 今回は約99km入力が距離検査通過、101kmで超過。公式の徒歩`max_distance`の既定値・許容上限は100,000m。標準のサービス設定は別に250,000m・50地点ですが、公開サーバーの設定と同一とは扱いません。51地点の入力はHTTP400 `InvalidValue`、正確な地点数上限はこの応答では分かりません。 | 変更後の手動検索は直線20km未満18秒、20km以上45秒、50km以上60秒。上流の負荷・検索計算量の制限は別です。 |
| Hosted openrouteservice | 公式公開制限：徒歩6,000km、回避ポリゴンあり150km、alternative/round-tripアルゴリズム100km、経由地点50。アプリの閉路は実座標列によるもので、専用round-tripオプションとは区別します。 | 既存の通常予備検索はPythonで接続5秒・読取60秒。キーはPython環境変数のみ。今回キー未設定のため、認証付きの実通信・6,000km経路は未検証です。 |

仕様：[Valhallaの歩行者設定](https://valhalla.github.io/valhalla/api/route/api-reference/#pedestrian-costing-options)、[ソースの上限値](https://github.com/valhalla/valhalla/blob/master/src/sif/pedestriancost.cc)、[標準サービス構成](https://github.com/valhalla/valhalla/blob/master/scripts/valhalla_build_config)、[Valhallaエラーコード](https://valhalla.github.io/valhalla/api/route/api-reference/#internal-error-codes-and-conditions)、[ORS公開制限](https://giscience.github.io/openrouteservice/hosted-api-restrictions)。

ソフトウェア既定値、公開サーバーの設定、経路の道のりを混同しません。実測からすべての地点での最大到達距離を保証するものではありません。

## 実装

1. 手動の長距離案内は通常経路を先に取得。20km以上の入力では、全区間を繰り返し問い合わせる坂道・コンビニ等の自動追加候補を省きます。近距離の候補・施設検索・寄り道検索は維持します。
2. 距離超過に加え、長距離でのタイムアウト・経路取得失敗等でも既存のORSへ切り替えます。ORS用の通信だけがタイムアウトしても親の処理全体を中止せず、その後の方法を試せます。
3. ORSを利用できないときは、既存Valhallaの[locate](https://valhalla.github.io/valhalla/api/locate/)で中継候補を確認して分割取得します。直線補間は道路を探す**検索の中心**にだけ使用し、目的地・描画用の経路として使いません。
4. 中継点は、APIの明示的な歩行者アクセス、接続性、既知の制限・目的地専用道・行き止まり・フェリー等を調べ、検索中心から1.2km以内の実際の道路上に選びます。情報不足の場合は保留します。
5. 次区間の出発位置には前区間の実際の終点を使います。接続のずれが0.5mを超える場合は不採用。各区間の到達点、徒歩モード、距離・時間、過大な迂回、全体の距離・点数も確認します。全区間の取得完了後だけ描画し、欠損を直線で埋めません。
6. 距離・時間はAPIが返した実経路の値を合算。途中の「到着」「出発」を最終目的地の到着と誤表示しません。改札内通路の除外・形状検査は各区間に維持します。
7. 距離超過、タイムアウト、経路なし、通信失敗、取得済みだが描画失敗を別のメッセージにしました。既存のルート表示／更新ボタンで再検索できます。既存の経路は再検索が失敗しても保持します。
8. 20km以上の道のりには所要時間と「長距離ルートです。所要時間に休憩は含みません。」を表示。スマホは従来どおり詳細を閉じて線を広く表示でき、閉じたボタンにも距離・時間が残ります。

処理量を抑えるため、分割は基準直線35km、280km超では各入力区間70km以内・最大16区間（直線約1,120km）、分割全体120秒以内、手動の長距離処理全体150秒以内です。通常・中継検索は既存の1秒以上の問い合わせ間隔を共有します。429や既知のサービス停止・入力地域の不接続等では同じ提供元へ分割を繰り返しません。地点・モード変更や終了で、待機・通信・古い結果を中止します。大量の点の結合に引数展開を使わず、スタック超過を避けます。

### 追加修正：直線280kmを超える場合

利用者のエラー文は、旧35km×8区間のアプリ上限で分割前に返していたものでした。範囲を拡張し、APIの入力距離と取得した道のりを区別して、取得済み区間の道のり100kmの不要な拒否も外しました。徒歩・端点・接続・迂回の検証と全体の時間制御は維持します。アプリ上限超過には専用の`AppRouteLimit`と約1,120kmの制限説明を使い、APIによる距離超過と区別します。

秋津付近〜広島駅の試験では、直線補間した検索中心の1つが琵琶湖上に落ちました。道路未確認の地点が最大3つまでの場合だけ、5km・10km周囲の東西南北各4地点を検索中心として追加確認します。API要求は追加2回・各12地点以内、最大の道路移動幅は10km＋1.2kmです。歩行アクセス・接続性の検証を通った道路座標だけを採用し、湖上の座標を経由地にはしません。不足が多い・情報が不明・通信が失敗した場合は取得を打ち切ります。

実通信では従来`DistanceExceeded`→分割上限エラーだった秋津付近〜広島駅が、**918.660km・10区間・29,773点・推定253時間31分49秒**で取得できました。分割は約24.805秒（最初の上限超過要求1.203秒は別）、初回locateと周辺再確認1回・10区間はすべてHTTP200です。区間同士のずれ0.5m以内・到達点・徒歩モード・過大な迂回の検査を通しています。最短経路を保証するものではありません。生応答はOS一時領域だけに保存します。

新しい有料API・ライブラリ・公開先は追加しません。ORSキーは引き続きPythonの `ORS_API_KEY` だけから読み、JavaScriptやログに出しません。6,000kmを直線区間の合計だけでも超えるORS要求は、送信前に公式の上限として拒否します。

## 変更ファイルと残る制限

- `static/js/long-routes.js`：中継・徒歩アクセス判定・連続性と迂回の検査・時間／件数制御。
- `static/js/app.js`：距離別の待ち時間、予備切替、キャンセル、APIエラーコード維持、端点検査、描画失敗の区別、注意表示。
- `index.html`、`templates/index.html`：共通モジュールの読み込み。
- `walking_routes.py`：ORSの公式6,000km制限の事前確認。Renderの起動・通信構成、環境変数の扱いは変更しません。
- `test_long_routes.cjs`、`test_walking_routes.py`、`test_tour.cjs`：新規・回帰テスト。`benchmark_long_routes.cjs`：明示実行用の実通信試験。
- README、外部利用条件、アプリ内出典台帳、本報告・集計：出典・制限・結果。

ORSの実用上限、回避ポリゴンによる150km制限、API計算量・混雑・利用上限は残ります。キーなし分割も最大16区間で、中継点を確認できない海・山・不接続地域、過大な迂回、つながらない区間は表示しません。最短を保証する分割ではありません。より遠い経路にはORSの設定が必要になる場合があります。元のAPIの足回り・アクセス情報や現地の通行状態に依存します。
