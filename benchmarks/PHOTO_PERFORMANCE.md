# 写真取得の高速化（2026-11-15）

施設・座標・所在地・ライセンスを照合する規則は変えず、通信と再利用を改善しました。新しいAPIや有料サービス、ライブラリは追加していません。公開環境へのデプロイ・pushは行っていません。

- 表示用サムネイルは640px指定から320px指定へ変更。今回のCommons応答では実際のURLが960pxから330pxになりました。拡大画面はAPIの大きい別サムネイルをクリック時に取得します。
- 地点が変わっても同じAPI問い合わせは10分間再利用。最大96件・UTF-8 JSON計6MiB、期限付きのメモリキャッシュです。別名・別画面から同じ駅の写真を開く際の再照会を減らします。
- 同時に届いた同一問い合わせを1回にまとめ、処理済みデータをコピーして各地点で座標・権利等を再判定します。APIエラーはキャッシュしません。「写真なし」からの再取得は共有キャッシュも使わず確認します。後続の[タイムアウト対策](TAKAO_AND_PHOTO_RECOVERY.md)では、未完了だった場合の再取得に成功済み照合応答を再利用します。
- Pythonの外部通信接続を最大2本の専用Sessionで再利用します。同時取得数2、外部呼び出し間隔250ms、最大8回・18秒目安の制限は維持します。
- 検証済みの成功メタデータを同一タブのsessionStorageへ最大50件・256Ki文字以内、元の24時間期限で保存します。再読み込みしても期限を延ばさず再表示できます。座標・名称等の公開目的地の参照と、著作者・出典・画像URL等だけを保存し、訪問日・メモ・散歩履歴や画像本体は保存しません。未取得・エラーの結果をsessionStorageへ保存しません。
- IntersectionObserverで画面内の写真だけ取得する制御を維持し、その後の画像に重ねて指定していたブラウザの遅延読み込みは外しました。画像のダウンロード開始が二重に待機するのを避けます。

## 実測

桜上水・青梅・秋津・新宿・東京・吉祥寺の6駅で、改善直前の処理と改善後を順に実行しました。両方とも6駅すべて同じ写真の出典URLを取得できました。

| 条件 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 各駅の初回・6駅平均 | 1.461秒 | 1.024秒 |
| 駅名に「駅」を付けて別の画面から取得・6駅平均 | 1.288秒 | 0.363秒 |
| 完全に同じ地点の再取得（メモリキャッシュ） | 約0.00003秒 | 約0.00003秒 |
| 桜上水駅の表示画像 | 153,603バイト | 21,647バイト |
| 青梅駅の表示画像 | 148,894バイト | 24,284バイト |

2駅の表示画像合計は302,497→45,931バイトで**約84.8%削減**です。容量が減っても通信時間が必ず同比率で減るわけではありません。今回のJPEG取得は改善前が0.64〜0.69秒、改善後が0.61〜0.73秒で、開発PCの通信待ち時間の影響が大きい結果でした。小さな画像は低速回線の転送量を減らすための改善です。

6駅平均の照合は約30%、別画面からは約72%短縮しました。ただし各ケース1回の開発PC上の比較で、全国の平均やRenderでの性能保証ではありません。最初の桜上水駅は接続の準備等を含み、1.125→1.414秒と遅くなっています。毎回すべての初回検索が速くなるという測定結果ではありません。既知の別画面キャッシュを含む条件を、完全な初回の数値と混ぜていません。施設検索・経路生成の時間は含めません。

個別の照合時間は [CSV](photo-performance.csv) を参照してください。基準にした取得率の113地点比較は [別レポート](PHOTO_BENCHMARK.md) の時点の数値で、今回その113地点をライブ再測定したわけではありません。

## 確認

自動テスト252件（Python 81・JavaScript 171）が成功。共有キャッシュの期限・容量、同時問い合わせの集約、失敗を保存しないこと、キャッシュを使っても別施設の座標を再検査すること、手動再取得、タブ内キャッシュの期限・不正値・保存不可・上限を確認しました。

ChromeではLive Serverと同じ別ポートから実APIへ接続し、桜上水駅・青梅駅の330px実画像を読み込みました。駅マーカー、再取得、スマホ幅390px、再読み込み後に写真API呼び出しを追加せず再表示できること、JavaScript例外なしを確認しています。実機Safari・本番Renderは未実施です。
