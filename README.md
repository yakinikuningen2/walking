# walking

場所を検索し、行った場所を地図に記録する散歩アプリです。

## 画面構成

PCでは左にナビゲーション、その隣に検索・登録・設定の操作パネル、右に地図を表示します。「地図」を選ぶと操作パネルを閉じ、地図の表示領域を広げます。スマートフォンでは地図の上にボトムシートを重ね、下部のメニューから画面を切り替えます。シート上部の取っ手を上に引くか展開ボタンを押すと大きくなり、下に引くと縮小・終了できます。iPhoneのセーフエリアにも対応しています。

「探す」には名前・住所の検索、出発地点、歩く時間、場所の種類、候補一覧をまとめています。雰囲気・方角・標高・キーワードは「詳細な条件」から設定できます。検索中の中止、ランダム検索、履歴、もっと見るも引き続き利用できます。時間・種類のショートカットは既存の入力欄と連動します。

スマホではルート詳細を閉じても距離・徒歩時間を小さなボタンに表示します。ボタンを押すと目的地や道順などの詳細を開けます。

配色・余白・角丸は`static/css/style.css`のCSS変数で管理します。検索窓はHTML/CSS、ナビゲーションなどの線画アイコンは独自のインラインSVGです。フォントはNoto Sans JP・IBM Plex Sans JPを優先するゴシック体のスタックを指定し、未インストール時は端末のフォントを使用します。外部フォントのダウンロードや新たな画像素材・ライブラリの追加はありません。

ボタンはホバー・選択中・押下中・無効状態を控えめな色の違いで表示します。ホバーは対応するマウスなどの機器だけに適用し、タッチ操作では押している間の色を表示します。リップル・影・拡大・フェードなどの装飾は追加しません。

| ファイル | 役割 |
| --- | --- |
| `index.html`・`templates/index.html` | 同じ画面構造・既存のフォームID・SVGアイコン。静的ファイルへの相対パスだけを切り替えます。 |
| `static/css/style.css` | 配色、タイポグラフィ、PCの3領域、スマホのボトムシートと下部ナビゲーション。 |
| `static/js/ui.js` | ナビゲーション、シートの開閉・展開、ショートカット、地図のサイズ調整。 |
| `static/js/route-nearby.js` | 選択中のルートに沿う寄り道検索、検索範囲の判定、候補一覧とキャッシュ。 |
| `static/js/app.js` | 既存の地図、位置情報、検索、ルート、ブラウザ保存。ルート詳細のスマホ判定を新しい画面幅に合わせています。 |
| `app.py`・`walking_routes.py` | 既存のHTTPサーバー・検索中継・ルートAPI。UI刷新による変更はありません。 |

検証コマンドは`node --test test_discovery.cjs test_navigation.cjs test_geolocation.cjs test_route_nearby.cjs test_natural_discovery.cjs`と`.venv\Scripts\python.exe -B -m unittest discover -v`です。UIの操作確認ではローカルのChromeと固定した検索・位置情報・ルート応答を用い、PC、スマホ、小さいスマホ、横画面、タブレットでナビゲーション、検索、保存、ルート、速度設定を確認します。実機Safari・公開Renderへのデプロイ確認とは別です。Renderの起動設定は下記のまま利用できます。

## 自然スポットと徒歩アクセスの検索

「探す」で歩く時間と「森・林」「川辺・湖畔」「海辺・浜辺・港」を選ぶと、既存のOverpass APIから自然スポットを検索します。名称が未登録でも対象にし、node・way・relationと複数の外周・内周を持つ形状に対応します。主なタグは次のとおりです。既存の湧水・滝・森林境界・漁港等のタグも維持しています。

| 種類 | 検索タグ |
| --- | --- |
| 森・林 | `natural=wood`、`landuse=forest` |
| 川辺・湖畔 | `waterway=river/stream`、`natural=water`、`water=lake/pond` |
| 海辺・浜辺・港 | `natural=coastline/beach`、`harbour=yes`、`leisure=marina` |

自然物の中心や輪郭上をそのまま目的地にはせず、地形から120m以内の地図上の道を探します。`highway=footway/path/pedestrian/steps/track`を先に取得し、その範囲で道を取得できなかった場合は住宅道路なども確認します。入口付近や公園内の道は候補名に反映します。最終的な目的地は必ず取得した道の線上の座標です。時間・方角はこの座標から再判定し、同じ道の同じ地点へ重複する自然物はまとめます。森・河川の中心から単に最寄り道路へ置き換える方式ではありません。

OSMに明示された私有地・立入禁止・歩行禁止・許可制・軍用・閉鎖・施錠などを除外し、既知の制限区域や通行不可のゲートに道がかかる場合も除外します。水面内の候補は、地図上の橋やトンネル等を除いて選びません。取得できた形状が不完全で水際を判定できない場合も候補を作らず、点だけの水辺で周囲の歩道を選べる場合は未確認とします。`foot=yes/designated/permissive`があっても現地確認済みとは扱わず、条件付きの通行指定・未記入・周辺制限情報の取得失敗や打ち切りがあれば「徒歩アクセス未確認」と表示します。歩道を取得できても制限情報に失敗した場合は、候補を未確認のまま残し、検索ステータスも一部取得失敗とします。

検索結果はリストとLeafletの葉のマーカーで表示します。マーカーからOSMの道の情報を確認し、目的地へ指定できます。「徒歩ルートを表示」は選んだ道上の座標を既存のPython `/api/walking-routes` へ渡し、サーバー側の`ORS_API_KEY`を使うORS徒歩ルートを先に試します。自然スポットからの通常ルートは待ち時間を15秒に制限し、ORS未設定・接続失敗等では従来の通常徒歩ルートへ戻ります。キーはJavaScriptや検索データへ渡しません。場所登録・検索履歴・近隣施設・他の種類の検索も維持します。以前保存した自然候補で歩道情報のないものは履歴を残したまま、目的地に指定する前に再検索を案内します。

負荷対策として、通常は要求半径30kmまでの矩形を対象とし、それより遠い場合は指定時間帯の周辺を最大4方向（方角指定時は最大3区域）に分けて確認します。各遠距離区域の半径は3.5kmです。自然物は種類ごと32件を目安に、打ち切り検知用の1件を追加取得し、形状を詳しく調べるのは通常最大12件、ランダム時4件、複数種類を探すときは各種類1件です。歩道・入口等は450mの小さい窓に限定して窓の重複を減らし、道は各窓65件、入口25件、公園17件、制限情報は合計65件までとします。大きすぎる形状も処理を制限します。全範囲・全件を確認できない場合はその旨を表示し、未確認を「見つからない」と断定しません。

問い合わせはOverpass側で通常8秒・周辺制限情報5秒、クライアント側で通常10秒・周辺制限情報6秒を上限とし、検索全体の既存60秒制限と中止処理も維持します。結果は10分間再利用し、自動で無限に再試行しません。正常な空応答、徒歩候補を確認できない場合、混雑・タイムアウト・APIエラーを区別し、取得済み候補を先に表示します。

2026-11-13の実データ確認では、秋津周辺の無名の森、柳瀬川、お台場の無名海岸・浜辺から、実在するOSMの歩道上の候補を取得しました。既存2提供元はタイムアウト／502だったため、固定した公開地点の検証には[OSM公式一覧](https://wiki.openstreetmap.org/wiki/Overpass_API)掲載の別の公開Overpass（VK Maps）も使用しました。アプリの送信先は既存の`overpass.private.coffee`と`overpass-api.de`のままです。取得済みの地形応答を一部再利用し、周辺制限情報は失敗したため未確認の注記を確認しています。現地の通行可否や公開Renderでの検索成功を保証する試験ではありません。

PC・スマホ画面のChromeでは取得した実データをローカルの固定応答として使い、3種類の検索・再検索、葉マーカー、注記、ポップアップの保持、履歴、目的地指定、ORSへの座標引き渡し、ORS未設定時の従来ルート、中止、空応答と混雑表示を確認しました。ORSの応答は試験用に固定しており、実ORS API・実機Safariは未検証です。新たなライブラリは不要です。公開時は`static/js/natural-discovery.js`、HTML2ファイル、CSS、`app.js`も含めて再デプロイしてください。出典・[ODbLの利用条件](https://www.openstreetmap.org/copyright)はアプリ内の「出典・ライセンス」とTHIRD_PARTY_NOTICESに記載しています。

自然検索導入後の自動テストはJavaScript 117件・Python 47件、計164件が成功しています。

## 外部データの出典・ライセンス

山、公園・緑地、街並み・集落、美術館・博物館、景色・観光、カフェ、食事、買い物、神社・寺院の条件検索は、同梱索引を先に探します。Wikidataの構造化データはCC0 1.0、GeoNamesはCC BY 4.0で、ライセンス別・種類別のファイルに分離しています。名称・座標・分類・識別子などを加工し、写真・解説文は使用しません。追加分は計55,896レコード（種類・提供元をまたぐ重複あり）、JSON計3,145,073バイト／gzip計923,596バイトです。桜・紅葉の既存データと神社16,983地点の索引も維持します。種類別件数と不採用理由は[調査結果の追補](DATA_RESEARCH.md)を参照してください。

初回は必要な種類だけJSONを読み込み、0.1度単位の空間索引を端末内に作成します。取得後は索引を再利用し、指定した出発地・歩行速度・時間の前後30分・方角で必ず再判定します。一致する候補は外部の施設検索を待たず表示し、未収録地域・読み込み失敗・時間帯に一致しない場合は従来の外部検索へ進みます。「こだわらない」では先に複数種類の同梱候補を表示し、未確認の種類を外部検索で補います。ランダム検索も既存の抽選処理で同梱データを利用します。雰囲気・標高の追加条件には従来の外部APIを使う場合があり、取得できないことを条件一致と扱いません。GeoNamesで明示された標高だけは保持しますが、DEM値は転用していません。

Renderを含むPython配信ではgzipと版付きURLの長期キャッシュを使い、Live Serverでも通常のJSONで動きます。起動時に全国データを展開せず、読み取り専用の静的データとして配信するため、新たなDBや依存ライブラリは不要です。表示時間は従来どおり直線距離×1.3からの推定で、実際の徒歩ルート・営業状況・入場可否・入口位置は別途確認が必要です。公開版へ反映するときは新しい2つの`static/discovery-*-jp-2026-11-13-v1/`フォルダ内のJSON・gzipとJSを含めてデプロイしてください。

## 使い方

1. 下記のコマンドでPythonサーバーを起動してから、VS Code の Live Server でルートの `index.html` を開きます。既存のLive Serverのアドレスを使えば、保存済みの歩く速さ・訪問記録をそのまま使えます。Pythonサーバーだけで使う場合は `http://127.0.0.1:8000/` を開くこともできます。
2. 起動時は初回も地図を表示します。歩く速さが未設定の場合は時速4 kmを使います。「設定」から速さ（ゆっくり：時速3 km／ふつう：時速4 km／はやめ：時速5.5 km）を選び、「保存」を押すと次回からもその設定を使います。バーはいつでも操作でき、動かすと自動で「数値で指定」に切り替わります。時速2.5〜6.5 kmを0.1刻みで調整でき、選んだ数値は「数値で指定」の右側に表示します（例：4.2 km/h）。キーボードの左右キーでも0.1ずつ調整できます。以前保存した数値が新しい範囲を外れている場合は、2.5または6.5に調整して復元します。ナビゲーションの「設定」（PCは地図右下の「歩く速さ」からも）でいつでも変更でき、そのときも背景の地図を表示したままにします。案内中は所要時間を含めてルートを計算し直します。
3. ナビゲーションの「登録地点」を押し、場所の名前や住所を入力して虫眼鏡を押すか Enter キーで検索します。候補を選ぶと候補一覧を閉じ、場所の登録欄を表示します。
4. 場所の名前・訪問日・メモを入力し、「保存」を押します。
5. 保存した場所を一覧から選ぶと地図に表示できます。編集・削除・直前の削除の取り消しもできます。

プロジェクトのフォルダで次のコマンドを実行します。追加パッケージは `requests` だけです。

```powershell
.\.venv\Scripts\python.exe app.py
```

ターミナルを開いたまま使います。終了は Ctrl+C です。PythonサーバーはこのPCの `127.0.0.1:8000` で動き、Live Serverからの地図情報の検索を中継します。起動していない場合は、従来どおりブラウザから検索APIへ接続します。ポートを変更する場合は `app.py --port 8001` のように指定し、表示されたPythonサーバーのURLから開いてください。

`app.py`・`walking_routes.py` の更新後は、起動中のPythonサーバーを Ctrl+C で止めてから起動し直してください。同じポートへの二重起動はエラーにして、古いコードと新しいコードが同時に応答することを防いでいます。

### Renderで公開する

Pythonの **Web Service** として公開できます。リポジトリ直下に `render.yaml` と `.python-version` を用意しています。まず今回の変更をGitHubへ反映し、追加した `static/seasonal-places.json` も含めてください。APIキーを含む `.env` 等はGitへ追加しません。

Renderで **New → Blueprint** からリポジトリを選ぶと、`render.yaml` の設定を使えます。**New → Web Service** から手動設定する場合は次の内容です。Static SiteではPython APIが動かないため、Web Serviceを選びます。

| 項目 | 設定 |
| --- | --- |
| Language / Runtime | Python 3 |
| Root Directory | 空欄（リポジトリ直下） |
| Build Command | `python -m pip install -r requirements.txt` |
| Start Command | `python -u app.py --host 0.0.0.0 --port $PORT` |
| Health Check Path | `/api/health` |

RenderのダッシュボードでStart Commandを設定する場合も、上記のコマンドをそのまま指定してください。`$PORT` はRenderの環境変数として展開されます。

`RENDER` の真値表記、または `RENDER_SERVICE_ID`・`RENDER_EXTERNAL_URL`・`RENDER_EXTERNAL_HOSTNAME` でRender環境を判定します。Renderでは必ず `0.0.0.0` と環境変数 `PORT` を使い、誤って `--host 127.0.0.1` や別の `--port` が指定されても上書きします。`PORT` が未設定の場合だけRender標準の `10000` を使い、不正な値なら起動エラーにします。ローカルでは従来どおり `127.0.0.1:8000` で起動し、`PORT` や `--host`・`--port` で変更できます。Pythonのバージョンは `.python-version` の `3.13` 系を使用します。

変更をGitHubへ反映後、既存のRenderサービスでは **Settings → Start Command** も確認し、最新のコミットをデプロイしてください。修正後の起動ログは `Walking map: http://0.0.0.0:10000/`（`PORT=10000` の場合）になります。まだ `127.0.0.1` が出る場合は、Renderが参照するブランチ・コミット・Root Directory・起動対象ファイルが今回のコードと一致しているか確認してください。

通常の徒歩ルート・場所検索・コンビニ検索・桜や紅葉の名所検索は `ORS_API_KEY` なしで利用できます。通常の検索で距離上限を超える長距離ルートや「出発地点に戻る」などORSを使う場合は、Renderの **Environment** に `ORS_API_KEY` を登録してください。値をJavaScript・HTML・`render.yaml` に書く必要はありません。

Renderが設定する `RENDER_EXTERNAL_URL` を使い、公開URLからのAPIアクセスを自動で許可します。通常は `WALKING_PUBLIC_ORIGIN` の設定は不要です。独自ドメインを使う場合だけ、そのHTTPSオリジンを `WALKING_PUBLIC_ORIGIN` に設定してください。

デプロイ後は公開URLの `/api/health` が `{"service":"walking-map"}` を返すことと、トップページ・場所検索・コンビニ検索を確認します。HTTPSの公開URLからスマホで位置情報を許可できます。訪問記録・歩行速度・検索履歴は端末のブラウザに保存するため、公開先を変えると以前のローカルURLの記録は引き継がれません。

`render.yaml` は無料プランを指定しています。無料プランは未使用時に停止するため、次回の最初の表示に時間がかかる場合があります。設定ファイルの用意とローカルでの起動確認まで行い、Render上への実際のデプロイは行っていません。

参照：[RenderのWeb Service](https://render.com/docs/web-services)、[Blueprint](https://render.com/docs/infrastructure-as-code)、[公開URLの環境変数](https://render.com/docs/environment-variables)、[無料プランの制限](https://render.com/docs/free)。

### スマホ向けの一時公開

Cloudflare Quick Tunnelで、このPCのPythonサーバーにHTTPSの公開URLを付けられます。PCとトンネルのプロセスが動いている間だけ利用でき、再接続するとURLが変わります。常時稼働するサーバーへの移設は行いません。

Cloudflare公式の `cloudflared` を用意し、1つ目のターミナルで次を実行します。今回用意した実行ファイルは `$env:TEMP\walking-map-server\cloudflared.exe` にあります。

```powershell
& "$env:TEMP\walking-map-server\cloudflared.exe" tunnel --no-autoupdate --protocol http2 --url http://127.0.0.1:8000
```

表示された `https://…trycloudflare.com` のURLを、別のPowerShellで次のように設定してPythonサーバーを起動します。既にPythonサーバーが動いている場合は、そのプロセスを先に終了してください。

```powershell
$env:WALKING_PUBLIC_ORIGIN = '表示されたHTTPSのURL'
# ORSを使う場合だけ、同じターミナルでORS_API_KEYも設定します。
.\.venv\Scripts\python.exe app.py
```

スマホのSafariでは公開HTTPS URLを開きます。検索APIはそのURLとローカルプレビューからだけ許可し、別サイトからのブラウザ要求は拒否します。`ORS_API_KEY` は引き続きPython側の環境変数だけに設定します。訪問記録・歩行速度はURLごとにブラウザ内へ保存するため、一時URLが変わると以前のURLの記録は自動で引き継がれません。URLを知っている人はアクセスできます。

詳細：[Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)。

速さの設定中は、どの項目を選んだあとでも矢印キーはスライダーだけを操作します。右・上で0.1 km/h増やし、左・下で0.1 km/h減らします。範囲は2.5〜6.5 km/hです。

検索で見つからない場所は、「場所を登録」を開いた状態で地図をタップ・クリックして選び、登録できます。登録画面を閉じている間は、地図を触っても登録地点を選択したり登録画面を開いたりしません。

検索・登録・設定はナビゲーションで切り替えます。PCでは表示中の操作パネルの分だけ地図の幅を調整し、スマホでは地図の上にシートを重ねます。

「歩く速さ」は「設定」から開けます。PCでは地図上の「歩く速さ」ボタンからも開けます。閉じても未保存の入力は保持します。別のメニューを選ぶと操作パネルを切り替え、検索の入力・表示済みの候補・履歴は保持します。検索画面を閉じると実行中の検索を中止します。スマホではシートを開いている間ルートの操作パネルを隠し、「地図」に戻ると再表示します。
保存した場所にメモがある場合は、地図のポイントの上に常時表示します。メモの編集・削除は地図上の表示にも反映されます。
パネルは閉じるボタンまたは「地図」メニューで閉じられます。検索・登録は Escape キーでも閉じられます。入力途中の内容は開き直しても残ります。マウス・タッチ操作に対応しています。
通常のホイール操作は地図の移動、Ctrl＋ホイールやタッチパッドのピンチは拡大・縮小です。

## 現在地

アプリを開くと現在地の取得を開始します。ブラウザの位置情報へのアクセスを許可すると、現在地を青い丸で表示して地図の中心を移動します。その後も位置情報を継続して受け取り、移動に合わせて青い丸と誤差の円を更新します。取得中に地図を操作したり目的地を指定した場合と、継続更新中は地図の表示位置・縮尺を保ちます。薄い青の円は位置情報の誤差の範囲です。

地図右下に「現在地」「現在地を追従」「歩く速さ」を縦に並べて表示します。「現在地」を押すと、縮尺を変えずに現在地へ戻ります。直近10秒以内・誤差50m以内の取得済み位置があればすぐに使い、古い場合は取り直します。高精度の継続更新も続けます。この操作ではルートを再計算しません。起動時の取得が終わっていない場合は、その結果を使って移動します。取得中・取得完了のメッセージは表示しません。「現在地を追従」をオンにすると、GPS更新ごとに縮尺を保ったまま地図の中心も現在地へ動かします。「追従をやめる」、地図のドラッグ・タッチパッドの移動操作、別の地点への移動で追従を解除します。追従の切り替え自体ではルートを再計算せず、現在地マーカーと方向矢印の更新は追従をオフにしても続きます。

起動時は、高精度の`watchPosition`と、最大10秒前までのブラウザキャッシュを許容する低精度指定の`getCurrentPosition`を同時に始め、先に得られた有効な位置を表示します。高速取得側は4秒、高精度側は15秒を指定し、一方のタイムアウトだけで他方を中止しません。高精度側が先に返った場合は、後着の高速取得結果を破棄します。30秒を超えた古い位置・新しく表示した位置より古い結果・直近の精度がよい位置から極端に精度が落ちる結果も反映しません。高速取得側の誤差が100mを超える場合は、その位置だけで徒歩ルートを開始しません。位置情報はページ内のメモリだけで再利用し、位置の永続保存や新しい外部APIの利用は行いません。ブラウザ・端末・電波状況による測位時間自体を保証するものではありません。仕様参照：[Geolocationの取得オプション](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition)。検証は`node --test test_geolocation.cjs test_navigation.cjs test_discovery.cjs`で行えます。

方角センサーを利用できる端末では、現在地の青い丸に端末の向きを示す矢印を重ねます。端末の向き・画面の縦横を変えると矢印も更新し、位置が変わると丸と一緒に移動します。方角の更新で地図の移動・拡大やルートの再検索は行いません。許可済みなどの状態でブラウザから方角データを受け取ると自動で表示します。iPhoneなどでセンサー利用が未許可の場合は取得できないことがあります。方角専用の許可ボタンは表示しません。方角が不明・コンパスが未調整の場合は矢印を表示せず、現在地の丸を表示します。センサーがないPCなどでは向きを表示できません。GPSの移動方向を端末の向きとして表示する処理はありません。方角はセンサーの精度や周囲の磁気の影響を受ける目安です。

地図は北を上に固定して表示します。地図自体を回転する操作には対応していません。

- HTTPS、または Live Server の `http://localhost:ポート番号`・`http://127.0.0.1:ポート番号` で開いてください。HTTP の LAN アドレスでは位置情報を取得できません。
- ブラウザと端末の位置情報の許可が必要です。許可拒否・取得失敗・タイムアウトは画面に表示します。
- 初回はブラウザの許可画面で「許可」を選ぶと、そのまま現在地を取得します。すでに拒否している場合や端末側の位置情報サービスがオフの場合は、ブラウザ・端末の設定で許可する必要があります。Web版から端末の設定を自動変更したり、iPhoneの設定アプリを直接開いたりする機能はありません。設定を変更してページに戻ると、許可エラーが出ていた場合は位置の取得を自動でやり直します。対応ブラウザではサイトの許可への変更も検知します。自動再取得では地図の表示位置・縮尺を保ち、手動で指定したスタート地点も変更しません。
- 表示中は `watchPosition` で現在地を継続更新します。更新間隔と精度は端末・ブラウザに依存し、画面ロック中やバックグラウンドでは更新が止まる場合があります。「現在地」を押したとき・現在地をスタートにした徒歩ルートの表示・更新時は、上記の直近位置の再利用または再取得を行います。追従がオフの場合はGPS更新で地図の中心を変更しません。条件検索の条件・結果はGPS更新で変更しません。案内中のルートは、下記の移動・逸脱条件を満たしたときだけ現在地から計算し直します。現在地を訪問記録として保存する処理はありません。

## スタート地点

「目的地を探す」を開き、画面上部の「スタート地点」の「検索」を押すと、名前・住所の検索欄を表示します。初期値は現在地です。場所の名前・住所を入力し、虫眼鏡か Enter キーで検索して候補を選ぶと、紫の丸でスタート地点を表示します。変更後も検索画面は開いたままです。別の場所を指定した場合だけ、検索欄の下に「現在地に戻す」を表示します。「現在地」など表示中のスタート地点名を押すと、スタート地点の検索欄を閉じます。右下の「現在地」ボタンは地図を現在地へ戻す操作で、選んだスタート地点は変更しません。

ルート案内と「条件で探す」は、このスタート地点を使います。検索した場所を選んだ場合は、位置情報を許可していなくても使えます。スタート地点を変えると案内中のルートを更新します。条件検索は検索開始時の地点・速さで続け、表示済みの候補も残します。候補はそのまま目的地として選べ、案内には最新のスタート地点と歩行速度を使います。指定はページを開いている間だけ保持し、再読み込み時は現在地に戻ります。

「現在地」「検索」と同じ行にある「地図で指定」から、直接地図をタップ・クリックしてスタート地点を決められます。紫のマーカーを置いて検索画面へ戻り、その地点をルート案内と条件検索の出発点に使います。地図の縮尺と表示位置は保ちます。「戻る」または Escape キーで指定をやめられます。「場所を登録」を開いて地図上の地点を選んだ場合も、登録欄の「スタート地点に指定」から設定できます。訪問記録を保存する必要はありません。

## 目的地

ナビゲーションの「探す」または地図の「目的地を探す」を押すと検索画面が開きます。名前・住所を入力し、虫眼鏡を押すか Enter キーで検索できます。徒歩時間と場所の種類はその下に、雰囲気・方角などは「詳細な条件」に表示します。開いたまま地図や現在地なども操作できます。閉じても入力・表示済みの候補・スクロール位置は保持します。

「名前・住所で検索」は地名・施設名・住所が分かる場所を探す機能です。「条件から探す」は徒歩時間・場所の種類・雰囲気などから行き先の候補を提案します。両者は見出しと区切り線で分け、それぞれの操作の下に結果を表示します。条件検索は「条件に合う場所を探す」から実行し、画面上部の経過時間にも「条件検索」と明記します。

候補を押すと、その場所を直接目的地に指定して検索画面を閉じます。目的地の指定時は地図の縮尺を変えず、表示の中心だけ移動します。

「場所を検索」の候補や地図上の場所を選び、「目的地に指定」を押すこともできます。登録地点は一覧や地図上の詳細表示からも指定できます。場所の名前や訪問記録を保存する前でも指定できます。目的地は赤い丸と「地図マーカーのアイコン素材4.png」のアイコンを合わせて表示します。

目的地を指定すると、地図右下に目的地の情報と「目的地を解除」ボタンが表示されます。「目的地を探す」から続けて別の目的地を検索できます。別の場所を指定すると目的地が切り替わります。入力中の訪問記録は保持します。目的地は現在のページ内で保持し、再読み込みすると解除されます。

## 条件から目的地を探す

検索状況は画面上部の経過時間の下に固定表示します。「候補を取得中」「周辺情報を確認中」「標高を確認中」「地形を確認中」を実際の処理に応じて切り替え、同じ処理で10秒以上待つと「応答待ち」も表示します。通信に失敗して待機する間は「検索先が混雑・再試行待ち」「通信エラー・再試行待ち」などの理由を表示します。取得済み候補がある場合は件数も添え、引き続き候補選択や「もっと見る」を利用できます。検索が正常に終了した時だけ「検索完了・候補○件」または「検索完了・条件に合う候補なし」と表示します。通信や追加情報の取得に失敗して検索を完了できなかった場合は「検索未完了」または取得失敗を表示し、候補が存在しないとは表示しません。検索の中止・条件変更後に以前の検索状況が上書きされることはありません。

候補は最初に5件表示し、未表示の取得済み候補がある場合は「もっと見る」を表示します。押すたびに5件ずつ追加し、取得済みの候補をすべて表示するとボタンを隠します。追加表示だけでは検索APIを呼び直しません。候補を選んで地図へ戻った後・検索画面を開き直した後・検索履歴を復元した後も、表示した件数と追加候補を保持します。条件変更や新しい検索では最初の5件に戻します。検索履歴は1検索あたり取得・判定済みの候補を最大250件保存します。田舎寄りは周辺情報を確認済みの候補、標高指定は標高を確認済みの候補だけを追加表示し、未確認の場所を候補として補いません。

「方角」で東西南北の4方向を指定できます。「指定しない」が従来の全方向検索です。検索時のスタート地点から見た方角を使い、選んだ方角を中心とする90度の範囲（左右45度）に入る候補だけを表示します。検索したスタート地点や地図で指定したスタート地点にも対応します。端末が向いている方向とは別です。方角は徒歩時間・種類・雰囲気・標高と組み合わせて使え、検索履歴にも保存・復元します。方角のない以前の履歴や、以前の斜め方向を指定した履歴も引き続き開けます。斜め方向の履歴から再検索する場合は4方向を選び直せます。

公園検索は指定した方角を優先する検索地点を使います。従来の検索でも地点型の取得範囲をその方角へ絞り、取得後に球面上の方位を確認します。森・水辺などの範囲は輪郭から目的地を選んだ後に方角を判定し、反対側の中心点だけで除外しません。桜・紅葉の名所にも同じ方角条件を適用します。

地図上の方角表示は現在地の向きを示す矢印だけとし、東西南北の表示や「方角を表示」ボタンは設けません。矢印は、許可済みのセンサー情報を取得できた場合に自動更新します。ページを開くたびに受信を試みますが、センサー未許可の端末では現在地の向きを推測して表示しません。地図は従来どおり北が上の固定表示です。

「公園・緑地」は、名前検索・近くのコンビニ検索でも使っているPhotonの種類フィルターを先に利用します。公園・庭園・自然保護区だけを取得し、指定の徒歩時間帯に合う候補が5件そろえば、広い範囲のOverpass検索を待たずに表示します。6時間30分なら、従来どおり6〜7時間の候補に限定します。近場だけで取得枠が埋まらないよう、時間帯の距離に合わせた検索地点を最大4方向に切り替えます。候補が少ない場合は、取得済みの候補を残して従来のOverpass検索で補います。端末からPhotonへの通信は最大8秒待ち、失敗した場合は同じ問い合わせをPythonの `POST /api/parks` 経由でも試します。中継への通信は最大10秒、Pythonからの接続・応答待ちはそれぞれ3秒・5秒です。両方が失敗した場合だけ従来のOverpass検索へ移ります。ほかの種類の候補取得は従来どおりです。

この公園検索では、約200m単位に丸めた検索地点と徒歩時間に応じた範囲を `photon.komoot.io` に送信します（ユーザー許可済み）。正確な出発座標と徒歩時間帯による再判定はブラウザ内で行います。種類・座標・地図IDが不正な候補や、取得情報で非公開・閉鎖と確認できる候補は除きます。料金・設備・入場可否を未取得の情報から推測しません。Photonの情報が網羅的である保証や、歩行時間が実際の経路と一致する保証はありません。取得データはページ内で10分間再利用し、GPSの小さな変化があっても再取得を減らします。

公開サーバー経由の公園検索でも送信先・場所の種類・丸めた座標・範囲は同じです。外部URLや種類を指定できる汎用中継にはせず、範囲・座標・要求サイズ・ブラウザのOriginを検証します。APIキーは不要です。成功した公園情報はPython側でも10分間保持します。新しいAPIを利用するには `app.py` と `static/js/app.js` の両方を反映して再デプロイしてください。

周辺情報をRenderから取得して502・503・504などで失敗した場合は、同じ既存のOverpass提供元へのブラウザからの通信も試します。1回の取得に設定された待ち時間は延長せず、不正な検索式は再送しません。追加の雰囲気情報を待つ間も取得済み候補の件数を表示し、候補の選択を続けられます。

雰囲気の周辺情報は候補ごとに10分間保持します。同じ公園が別の候補の組み合わせに入っても取得済みの情報を再利用し、未取得の候補だけを問い合わせます。「田舎寄り」は引き続き周辺情報の確認が済んだ候補だけを表示します。

確認方法：徒歩時間を6時間30分、種類を「公園・緑地」、雰囲気を「こだわらない」にして検索します。候補が検索時の目安で6〜7時間に収まること、再検索やわずかなGPS移動後には取得済みデータを使うこと、候補選択・履歴・中止が使えることを確認します。桜上水駅・3時間30分・自然が多いでは3〜4時間の候補が対象です。雰囲気や標高を指定した場合は、それぞれの追加情報取得に時間がかかることがあります。端末のPhoton通信が遮断されても `/api/parks` の応答で候補を表示できること、Pythonの中継がない場合は従来検索へ移ることも確認できます。自動テストは `node --test test_discovery.cjs` と `.\.venv\Scripts\python.exe -B -m unittest test_walking_routes test_park_search -v` で実行できます（外部通信なし）。

スマートフォンでは検索画面を開いてもキーボードを自動では出しません。見出し・閉じるボタン・検索時間をスクロール領域の外に置き、検索欄と条件・候補だけをスクロールします。キーボードやブラウザの表示領域の変化に合わせて高さを調整し、入力中の欄を画面内に保ちます。

「目的地を探す」の名前検索欄の下に、条件を並べて表示します。開いている間も地図の移動・拡大縮小、名前での目的地検索、現在地などを操作できます。条件検索中に名前検索をしても、条件検索は続きます。経過時間は画面上部に表示します。

片道の徒歩時間を「時間」と「分」で入力すると、指定時間の30分前〜30分後の範囲から候補を探します。たとえば2時間なら徒歩1時間30分〜2時間30分、6時間なら徒歩5時間30分〜6時間30分の場所が対象です。下限が0分を下回る場合は0分にします。5分以上で指定でき、時間の上限はありません。入力欄の下にも対象の時間帯を表示します。種類の初期表示は選択できない「条件を検索」で、通常の条件検索では種類を選ぶ必要があります。選択肢は「こだわらない」、自然、季節の名所、街歩き・観光、飲食、買い物の順です。「散歩先」は選択肢から削除し、過去の「散歩先」の履歴は候補を残したまま「こだわらない」で再検索できるようにしています。「こだわらない」では公園・山などの自然の場所からカフェ・神社・買い物先などまで対象にします。徒歩時間・方角・雰囲気・標高の条件と60秒の待ち時間上限を適用し、検索履歴にもこの選択を保存します。駅は近隣検索で探せます。

「こだわらない」は公園の高速検索（Photonと既存の中継）を使いながら、ほかの種類も探します。カフェ・神社・観光などの地点は最大3種類ずつまとめて問い合わせ、候補がない種類をまとめて確認します。各種類の取得枠とキャッシュは独立し、森・湖・海岸など輪郭が必要な種類は別に取得します。同時に処理するまとまりは最大2つです。公園のPhoton検索で同じ範囲が空だった場合は、順位付けの中心だけを変えた重複問い合わせを省き、Overpassで確認します。正常な空応答を確認したら待ち時間を使い切らずに終了し、空応答も10分間キャッシュします。通信失敗や不完全な応答を「候補なし」として保存しません。

見つかった候補は検索途中から表示・選択できます。5件・3種類という件数での打ち切りはせず、残りの種類も検索します。表示順は種類ごとに1件ずつ交互にし、最初の5件が公園だけで埋まらないようにします。各種類の中では従来の順位を保ち、履歴や「もっと見る」でも同じ並び方を使います。一部の種類の通信が失敗した場合は取得できなかった旨を表示し、全件取得できない場合は「検索未完了」とします。桜・紅葉のキーワードは引き続き同梱データを使います。確認方法は徒歩時間6時間・種類「こだわらない」で検索し、5時間30分〜6時間30分の候補が途中から表示されること、ほかの種類が最初の5件にも混ざること、再検索がキャッシュを使うこと、「中止」や条件変更で以前の応答が混ざらないことを確認します。外部検索先の混雑・停止時は候補の取得を保証できません。

時間入力の下の「ランダムに探す」は、徒歩時間だけで散歩先を1件提案します。場所の種類・雰囲気・方角・標高・キーワードは使わず、検索時のスタート地点と保存済みの歩行速度で同じ前後30分の時間帯を判定します。種類をランダムな順で最大2種類まで並行検索し、先に候補が見つかった検索の取得済み候補から1件をランダムに選びます。残りの通信は中止します。1種類を待つのは最大8秒で、遅い種類があっても別の種類を探せます。地図データの取得は1種類60件・サーバー処理5秒、輪郭の追加取得は4件ずつに抑え、通常の条件検索用のキャッシュとは分けます。種類ごとの上限によるサンプリングと先着順のため、地域内の全地点を均等な確率で抽選するものではありません。取得できた候補を最大500件・10分間保持し、再抽選は通信せずに候補から選びます。その都度、最新の検索開始地点・歩行速度・指定時間で再判定し、範囲外の候補は使いません。取得に失敗した種類があり、ほかにも候補がなければ「検索未完了」とし、「候補なし」と区別します。候補の時間は通常検索と同じ直線距離からの概算で、目的地に選んだ後にルートを計算します。経過時間・検索中の表示・中止・目的地の設定・検索履歴は通常の条件検索と共通です。

雰囲気は「都会寄り」「田舎寄り」「自然が多い」から選べます。「山」「海辺」「田舎 森」のように希望欄へ短い言葉を並べても使えます。「山」などで希望した種類が近場にない場合は、概算の徒歩時間内で検索範囲を広げます。「散歩先」で「田舎 カフェ」と指定した場合は、希望したカフェも検索対象に加えます。雰囲気・希望した種類・名前の一致を候補の優先順位に反映します。「田舎寄り」は周辺確認を通った場所に絞り、都会や未確認の候補で件数を埋めません。「都会寄り」「自然が多い」は従来どおり希望に近い場所を優先します。選択した場所の種類と、概算での徒歩時間を条件にします。希望欄は対応する短い言葉と名前・説明の一致を使い、任意の自然文全体を解釈する機能ではありません。

「標高が高め」にチェックすると、徒歩時間・種類・雰囲気に合う取得済みの候補から最大24件の標高を比較し、高い順に最初の5件を表示します。6件以上ある場合は「もっと見る」で続きを表示できます。「高台」「高原」「標高が高い」と希望欄に入力しても使えます。海抜300mなどの固定の下限は設けず、取得できた候補の中で比較します。地図に記載された標高がなければ、既存の [Valhallaの標高API](https://valhalla.github.io/valhalla/api/elevation/api-reference/) で候補の座標をまとめて調べます。森や湖などの範囲は中心や山頂ではなく、目的地として使う輪郭上の座標で調べます。結果には「標高 約120 m」のように目安を表示し、標高不明の候補はこの条件では表示しません。標高データは10分間再利用します。標高条件と結果の数値も検索履歴に残ります。

「田舎寄り」は、都会らしさが少ない場所も含むアプリ内の目安です。[田畑](https://wiki.openstreetmap.org/wiki/Tag:landuse%3Dfarmland)や[集落](https://wiki.openstreetmap.org/wiki/Tag:place%3Dhamlet)が近くにあることを必須にせず、周辺情報を取得したうえで、中心市街地や店の密集などがなければ候補に含めます。田畑・集落は800m以内、山・森は少し離れた2km以内まで考慮し、それらがある候補を優先します。都会らしさは目的地から400m以内で判定し、都市の中心・大型商業施設・工業地、店や対象施設が6件以上ある場所、商業地と住宅地が重なって店などが3件以上ある場所を除外します。小さな商業区画や住宅地だけでは除外しません。駅以外の場所にも同じ基準を使い、地域名のブラックリストは使いません。

周辺情報の通信が終わるまでは「田舎寄り」の候補を表示せず、通信に失敗した場所も表示しません。正常に取得できた場合は、田畑・山林・集落の登録がなくても、都会らしさが少ない候補を表示できます。候補なしと通信失敗は短いメッセージで区別し、検索中の取得・確認件数や判定基準の説明文は画面に表示しません。経過時間・かかった時間と対象の徒歩時間帯は引き続き表示します。希望欄に「田舎」と入力した場合にも同じ基準を使います。地図の登録状況による差があるため、行政上の区分や人口密度を使った正式な田舎の定義ではありません。

保存した歩行速度と現在地から候補を探します。通常の条件検索は対象の時間帯全体を最初から検索し、候補がないときに近場から範囲を広げて同じ地域を取り直す処理を減らします。候補は常に指定時間の30分前〜30分後に収まるものに絞ります。ランダム検索の軽量な試行は、小さい範囲から探す方式も維持します。

「海辺・浜辺・港」は砂浜・海岸線に加え、`harbour=yes/fishing/marina`、`leisure=marina`、`landuse=harbour/port`、`industrial=port`、`water=harbour`の港・漁港・マリーナも対象です。希望欄の「港」「漁港」「港湾」「マリーナ」も海辺の希望として扱います。非公開・徒歩禁止と確認できる地点は従来どおり除外し、水域の中心点を徒歩目的地にしません。参照：[OSM harbour](https://wiki.openstreetmap.org/wiki/Key:harbour)、[marina](https://wiki.openstreetmap.org/wiki/Tag:leisure%3Dmarina)、[port](https://wiki.openstreetmap.org/wiki/Tag:landuse%3Dport)。既存サービスから取得し、新しい外部APIや同梱データは増やしていません。

候補を選んで地図に戻ったあとも、検索条件・候補一覧・スクロール位置を保持します。「条件で探す」を開き直すと、再検索せずに別の候補と比較できます。GPSで現在地が移動した場合や、スタート地点・歩く速さを変更した場合も、検索中の処理と表示済みの候補を保持し、再検索を要求しません。候補の時間・距離は「検索時の目安」として表示します。直近10件の検索条件と候補一覧はブラウザ内に保存し、「検索履歴」から過去の検索も呼び戻せます。再読み込み後は、最新の検索結果を復元します。ルート案内は最新のスタート地点と歩く速さで行います。

公園・山頂など、地点の座標を使う種類は検索先でも対象の距離帯に絞ってから取得します。近場の場所が取得枠を埋め、6時間〜7時間などの遠い場所が取得前に漏れることを防ぎます。種類ごとに取得枠を分けます。通常は矩形の範囲検索と座標からの距離条件を併用し、取得後に球面距離で時間帯を再確認します。極地・日付変更線付近や半径100km超では距離条件をブラウザ側だけで確認します。森・湖などの範囲は中心点だけでは除外せず、輪郭を取得して到着地点の時間を確認します。[Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL)の出力上限はブラウザで絞る前に適用されるため、地点は時間帯を先に絞る必要があります。

「歩ける時間」は候補の検索範囲に使う時間で、検索処理の待ち時間とは別です。検索画面上部と検索中のボタンに経過秒数を表示し、終了・中止後にはかかった時間を残します。検索結果が空と確認できればすぐ終了します。通信が停止したまま検索中にならないため、各まとまりに8秒、全体には60秒の安全用タイムアウトを残しています。地点の一括取得は通信ごとに最大6秒です。条件検索に使うOverpassは、最初の検索先が1秒で応答しなければ予備にも問い合わせ、先に返った結果を使います。両方が失敗した場合は自動再試行を繰り返さず、失敗として終了します。正常な空応答は「検索完了・条件に合う候補なし」、通信失敗や時間切れは「検索未完了」と区別します。確認済みの候補は、追加検索が時間切れになっても残します。「中止」や画面を閉じる操作は通信を止め、表示済み候補を保持します。条件を変更すると一覧を消し、以前の候補は検索履歴に残します。ブラウザがバックグラウンドになる等でタイマーが遅れる場合は、厳密な60秒での終了を保証するものではありません。

「ランダムに探す」の横と条件検索ボタンの横には「中止」を常に表示します。検索していない間は無効で、条件検索・ランダム検索のどちらを実行していても両方のボタンで中止できます。表示済み候補は消しません。通常の検索・ランダム検索が終了したら、候補がある場合は検索パネル内を候補一覧までアニメーションなしでスクロールします。地図の位置や縮尺は変えません。候補がない場合は結果メッセージを確認できる位置を保ち、中止時には自動スクロールしません。

PCの「探す」は上部の取っ手をつかんで移動できます。移動先は表示範囲内に制限し、端まで寄せられます。スマホでは取っ手の上下操作をシートの展開・縮小に使います。閉じるボタンや入力欄の操作はドラッグにしません。画面サイズ変更やソフトウェアキーボードの表示時には検索欄を表示範囲内に調整します。

候補ごとの経路計算は行わず、直線距離を1.3倍して一般的な回り道を見込み、設定した歩行速度で所要時間の目安を出します。概算で表示中の時間帯に収まる候補を、希望への近さ・所要時間の順に5件ずつ表示します。取得できた候補は残りの周辺情報の確認や追加検索を待たずに選べます。候補を押すと目的地に指定でき、地図の縮尺は変えません。「徒歩ルートを表示」を押したときに実際の経路と所要時間を計算します。滞在時間と帰路は含みません。

最初は地点名・座標などの軽い情報だけを取得します。森・川・湖・海岸などの輪郭が必要な場所は、候補が足りないときに地図IDで最大12件ずつ追加取得します。全件の細かい輪郭を最初から取得しないことで通信量を減らします。川・湖の中心や、未確認の森林の中心を代わりの目的地として表示することはありません。取得済みの輪郭も10分間再利用します。[Overpassの公式説明](https://dev.overpass-api.de/overpass-doc/en/full_data/bbox.html)でも、大きな関係データの形状を出力すると通信量が増えるため、必要な範囲に絞る方法が説明されています。

- 雰囲気は最大8候補ずつ（「田舎寄り」は4候補ずつ）、目的地の座標から周辺情報をまとめて取得して推定します。「田舎寄り」は4候補の確認が終わるたびに表示を更新し、後続の通信に失敗しても表示済みの候補は残します。店・施設は400m、「田舎寄り」の土地情報などは800m、山・森だけは2kmまで調べます。矩形検索で取得し、判定時には実際の距離で絞ります。候補ごとに土地など80件・店16件・施設16件・離れた山や森40件の取得枠を分け、混雑した場所だけで他の候補の取得枠が埋まることを防ぎます。大きな森・湖の形状全体を起点に検索しないため、離れた街の情報を混ぜずに確認できます。「田舎寄り」は周辺情報を取得できた候補が5件そろうか対象がなくなるまで次の候補も調べます。取得した周辺情報は10分間再利用します。各候補の雰囲気表示は目安です。
- 「無料」と表示するのは地図に無料と明記され、条件付き料金が設定されていない場所だけです。設備は場所自体の地図情報に記載されている場合に表示し、周辺設備だけの追加検索や優先条件は設けていません。未登録の料金・設備を推測して表示しません。営業時間や混雑、設備までの通行可否は判定しません。
- 候補の時間は道路や入口を調べる前の概算です。川・線路・私有地などにより大きく回り道する場合や、徒歩で到達できない場合があります。実際のルート案内で確認できます。
- [山](https://wiki.openstreetmap.org/wiki/Tag:natural%3Dpeak)は山頂の地図上の点を使います。[森・林](https://wiki.openstreetmap.org/wiki/Tag:natural%3Dwood)は地図上の森林・林の範囲を使い、川・湖・海岸も候補に含めます。範囲のデータがある場所は現在地に近い輪郭上の点を使い、川や湖の中心は目的地にしません。輪郭は検索範囲付近だけ取得し、種類ごとに取得枠を分けて、特定の種類だけで候補が埋まるのを防ぎます。輪郭上の点が実際の入口・遊歩道であるかは未確認です。山の標高差・登山道の難しさは概算時間に反映していません。
- 現在地・検索範囲、候補の座標や輪郭を調べる地図IDを [Overpass / Private.coffee](https://overpass.private.coffee/) と [Overpass API](https://overpass-api.de/) に送ります。直前に応答した検索先を優先し、応答がない場合や失敗時にもう一方を利用します。Pythonサーバーの起動中は同じ内容を `requests` でPOST送信します。Live Serverから直接検索する場合もフォーム形式のPOSTを使い、長い検索式をURLに含めません。送信先は従来と同じです。ブラウザから通信を中止しても、中継サーバー側の通信は完了またはタイムアウトまで続く場合があります。条件検索中に経路計算は行いません。「標高が高め」を使う場合は、標高が未登録の候補の座標だけを既存の Valhalla の標高APIへ送ります。ルート案内では Valhalla に現在地・目的地・経由地の座標と歩行速度を送信します。標高取得と経路計算は1秒以上の間隔を空けます。検索履歴には検索条件・検索時の出発地点・候補をブラウザ内だけに保存し、履歴一覧を外部に送信する処理はありません。
- 施設・周辺情報は最大10分、ページを開いている間だけキャッシュします。直前に取得できた検索先を優先し、失敗した検索先への再接続は30秒以上空けます。雰囲気の追加情報も4秒で応答しなければもう一方へ問い合わせ、各通信は最大15秒待ちます。追加情報を取得できなくても確認済みの候補は残しますが、「田舎寄り」の未確認候補は表示しません。外部サービスが停止している間は、待っても候補を取得できないことがあります。「中止」でいつでも止められます。

## 桜・紅葉の名所

名所の情報は `static/seasonal-places.json` に収録しています。桜76地点・紅葉59地点、重複をまとめて131地点です。収録地点から、保存済みの歩行速度と指定時間の前後30分に合う候補を5件ずつ表示します。「もっと見る」・候補の選択・目的地の設定・検索履歴はほかの条件検索と同じです。標準の「こだわらない」での名所検索は同じサイト内の固定データだけを読み込み、現在地や検索条件を外部へ送信しません。雰囲気・標高の追加条件には従来の周辺情報・標高APIを使います。

名所の分類はWikipediaの[日本さくら名所100選](https://ja.wikipedia.org/wiki/日本さくら名所100選)・[日本紅葉の名所100選](https://ja.wikipedia.org/wiki/日本紅葉の名所100選)、座標は各記事および [Wikidata](https://www.wikidata.org/wiki/Wikidata:Licensing) を使い、個別の出典もデータ内に記録しています。Wikipedia由来の編集・分類はCC BY-SA 4.0、Wikidataの構造化データはCC0 1.0です。本文・写真は含みません。再配布条件を確認できなかったGO TOKYO由来の地点・分類は除外しました。座標や適切な代表点を確認できない一部の広域名所は収録していません。

収録済みの名所を検索する機能で、すべての花見・紅葉スポットを網羅するものではありません。現在の開花・色づき・開園状況は取得しません。地点は代表点であり、入口や実際の歩行経路・所要時間はルート案内で確認してください。

## 近くのコンビニ・駅・トイレ・バス停

地図上の「近くの」で「コンビニ」「駅」「トイレ」「バス停」を切り替え、「探す」で現在地から直線距離1km以内の地点を強調します。種類ごとのアイコンと凡例で表示します。検索結果が表示中、または検索中に種類を切り替えた場合は古い通信・マーカーを消し、選んだ種類を検索します。現在地を取得できていない場合は、表示中の地図の中心から探し、そのことを件数欄に表示します。現在地を使う場合は検索開始時に縮尺を変えずに現在地へ戻ります。結果の取得後は地図の表示位置・縮尺を変更しません。

バス停は国土交通省の[P11-2022](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P11-v3_0.html)を優先して検索します。278,515レコードを47都道府県へ分割し、最初は小さな索引だけを読み、検索範囲にかかる地域だけを取得します。各地域は約5kmの区画で索引化し、近くの区画だけを調べます。秋津駅では東京都・埼玉県の2地域だけを読み、読み込み済みの地域を再利用します。JSON合計19,699,540バイト、gzip合計4,648,755バイト（索引を除く）。Python／Renderでは圧縮配信し、Live Serverでも通常のJSONで動作します。

トイレは東京都・国土交通省の[車椅子使用者対応トイレ情報](https://ckan.hokonavi.go.jp/dataset/facility_tokyo_bf-toilet)を優先します。都内4,857施設の代表座標を収録し、住所・設備の利用時間・備考を保持します。駅の改札内などへ案内しないため、原典の交通施設は除外しています。原典は令和6年度更新版、配布元のデータ更新日は2026-03-19です。JSON 1,462,166バイト、gzip 322,287バイト。地図上とアプリ内に出典を表示します。現在の利用可否・正確なトイレ入口・全国の網羅を保証するものではありません。

同梱データが読み込めない、または1km以内に候補がない地域では、従来のOverpassへ切り替えます。OSMでは[`amenity=toilets`](https://wiki.openstreetmap.org/wiki/Tag:amenity%3Dtoilets)、[`highway=bus_stop`](https://wiki.openstreetmap.org/wiki/Tag:highway%3Dbus_stop)、バス用の[`public_transport=platform`](https://wiki.openstreetmap.org/wiki/Tag:public_transport%3Dplatform)、バスターミナルが対象です。私有・利用者限定・廃止済みなどと記録された地点を除き、通信失敗と候補なしを分けます。候補なしは「地図データにない」という意味で、現地に存在しないとは断定しません。

外部APIを使う場合も約200m単位に丸めた地点を基に、1.2kmを覆う矩形だけを検索します。最初の検索先が1秒で返らなければ予備にも問い合わせ、通信は各10秒で打ち切ります。自動再試行はしません。取得済みの結果は種類別に10分間再利用し、実際の現在地から1km以内へ絞ります。「消す」は通信を中止し、到着が遅れた結果を表示しません。

秋津駅（35.7787, 139.4966）の実データをローカルのPython gzip配信から読むChromeの確認では、バス停18件（秋津駅北口・新秋津駅など）を表示し、外部APIへの問い合わせは0回でした。PCで初回約90ms／再検索約3ms、スマホ表示で初回約107ms／再検索約4msでした。公開サイトの回線・サーバー起動状況による時間は別です。バス停は2022年度時点のデータで、乗車側の位置・現在の運行状況・新設停留所が常に反映されるものではありません。

再生成は`build_bus_stop_index.py P11-22_GML.zip`、`build_toilet_index.py facility_tokyo_barrier-free_toilet.zip`で行います。原本ハッシュ・取得元・利用条件は[THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)に記録し、元ZIPはリポジトリ外に保持します。デプロイ時は新しいJSON・gzipを含めてGitHubへ反映してください。

国内の駅は、同梱の `static/stations-jp-2025-v1.json` を優先します。[国土数値情報（鉄道データ・2025年度）（国土交通省）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N02-2025.html)の駅10,234地物を、公式の駅グループコードに従って9,046組にまとめています。初回だけ同じサイトから読み込み、緯度経度0.1度ごとの索引を端末内に作ります。検索地点にかかる区画だけを調べ、実際の現在地から1km以内に絞るため、収録駅が見つかる検索では現在地を外部へ送らず、検索APIの混雑も待ちません。別の地域での再検索も索引を使い回します。改札内通路の回避情報は駅データと並行して読み込みます。

索引の近くの区画に収録駅がない場合、またはファイルを読み込めない場合だけ、従来のOverpassサービスで `railway=station|halt` を検索します。海外などの検索もこの代替手段を使います。Photonに送る検索の種類は増やしません。Overpassにはコンビニと同じ約200m区画・1.2kmを覆う矩形を送り、各10秒で打ち切ります。種類ごとの結果キャッシュ・同名の駅の重複除去・中止後の古い結果の破棄も維持します。秋津駅は、確認済みの駅外側の入口のうち検索地点に近い入口を目的地に使います。ほかの収録駅は駅区間の中点を代表位置として使います。

駅データの基準日は2025年12月31日です。その後の新設・改称・廃止が常に反映されるものではありません。元の線形状を区間長の中点へ変換し、公式グループの代表駅と路線・運営会社をまとめて本アプリ用に加工しています。ライセンスは[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)で、元データの出典・加工内容・ライセンスをJSON内に記録し、駅を表示すると地図の出典欄にもリンクを出します。政府によるアプリの作成・推奨を示すものではありません。

JSONは733,060バイト、事前圧縮した `.json.gz` は176,444バイトです。Pythonサーバー／Renderでは、gzip対応ブラウザに圧縮版を返します。版付きのURLだけを長期キャッシュし、通常のHTML・JSや通行除外情報の再検証は変えません。Live Serverでは通常のJSONのまま使えます。`build_station_index.py` は公式 `N02-25_GML.zip` のSHA-256を確認して同じJSONとgzipを再生成します。追加ライブラリは不要です。再生成例：`.\.venv\Scripts\python.exe -B build_station_index.py "C:\path\N02-25_GML.zip"`。別年度や修正版へ更新するときは出典・チェックサム・基準日を確認し、ファイル名の版とJSの参照先も更新してください。公開時はJSONとgzipの両方をGitHubに含めます。

速度の確認：実際の同梱データを実際のPython gzip配信から読む、スマホサイズのChrome・ローカル固定地点試験では、秋津付近の初回検索104ms、再検索3ms、東京への地点変更後4msでした。秋津・新秋津を表示し、いずれの収録駅検索も外部地図APIへの問い合わせは0回でした。これはローカルでの測定で、公開サイトの初回読み込み時間は回線とサーバーの起動状態にも依存します。自動テストは `node --test test_navigation.cjs test_discovery.cjs` と `.\.venv\Scripts\python.exe -B -m unittest test_station_index test_walking_routes test_park_search -q` で、索引境界・距離・別地域での再利用・代替検索・中止・gzipとキャッシュの互換性を確認します。

マーカーを押すと名前と登録されている住所、駅では路線・運営会社を確認でき、「目的地に指定」もできます。「消す」でマーカー・件数表示を消せます。検索中に押した場合は通信も中止します。ルート・現在地・訪問記録はそのまま使えます。

コンビニは、名前検索で既に使っている [Photon](https://github.com/komoot/photon/blob/master/docs/api-v1.md#reverse) の周辺検索を優先します。ボタンを押したときだけ、検索地点を含む区画の中心座標と検索半径1.2kmを `photon.komoot.io/reverse` に送り、`shop=convenience` の地点を最大50件取得します。区画の中心は緯度・経度を0.002度単位に丸めた位置で、現在地の座標そのものは送りません。取得した地点を現在地からの距離で絞り、1km以内を近い順に表示します。APIキー・Pythonサーバーは不要です。

Photonに接続できない・5秒以内に応答しない場合は、従来のOverpassサービス（`overpass.private.coffee`／`overpass-api.de`）へ同じ区画周辺の矩形範囲を送ります。Pythonサーバー起動中は既存の中継を利用します。この場合は最大500件を取得し、1km以内を最大200件表示します。Overpassの最初の検索先が1秒以内に応答しなければ予備にも問い合わせ、先に取得できた結果を使います。通信は各10秒で打ち切り、自動再試行はしません。

結果は約200mの区画ごとに最大10分間、ページを開いている間だけ保持します。再検索時には現在地からの距離を計算し直すため、GPSの小さな変動で同じ問い合わせを繰り返しません。同名で約20m以内の重複、検索結果に立入禁止・閉店情報がある地点を除きます。営業時間や実際の営業状況の確認は行いません。タイムアウトと混雑は表示を分け、「消す」で通信を中止できます。どの検索先も利用できない場合は、エラーを表示して再検索できる状態に戻します。

## 徒歩ルート案内

### ルート沿いの寄り道を探す

徒歩ルートを表示し、地図上の「近くの」を「ルート沿い」へ切り替え、場所の種類を選んで「探す」を押します。ルート詳細の「ルート周辺の寄り道を探す」からも開始できます。コンビニ・駅・トイレ・バス停に加え、カフェ・公園・緑地・景色（展望スポット）・神社・寺院を選べます。ルートがない間は「ルート沿い」を選べません。

複数の線が表示されている場合は、選択中のルートが対象です。出発地点付近だけでなく、曲がり角や途中区間も含めて、ルートから直線距離300m以内の代表位置を持つ地点を抽出します。ルートを囲む四角形の内側にあるだけの地点は含めません。候補はルートの出発地点からの順で最大200件を表示し、一覧は8件ずつ「もっと見る」で増やせます。距離は追加の徒歩距離・入口までの距離ではなく、施設の代表点からルートまでの距離です。

候補を押すと縮尺を保ってその地点を表示します。候補の表示・検索・閲覧だけでは目的地やルートを変更しません。マーカー内の「目的地に指定」を押すと、既存機能と同じく目的地を変更します。複数の経由地を追加して元の目的地へ案内する機能ではありません。候補欄は見出しで開閉でき、歩行に伴うルート更新でも閉じた状態と「もっと見る」の表示件数を保ちます。「消す」で検索中の通信・マーカー・一覧を消せます。

駅・バス停・東京都のトイレは既存の同梱データを優先し、候補が得られた場合は外部APIを待ちません。他の種類や同梱データが使えない地域は、既存のOverpassサービスを利用します。この際はルートの座標列と検索半径（判定用300mに余白を加えた360m）を送ります。APIキーや新しい外部サービスは追加していません。[Overpassの線に沿った周辺検索](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL#Around_(around))を使い、長い座標列は分割して最大2件ずつ検索します。敷地の入口・営業時間・現在の利用可否は原典の収録状況によります。

外部検索の結果はページを開いている間だけ10分間再利用します。ルートが少し短くなっただけで前回の取得範囲に収まる場合も再利用します。別のルートに切り替えた場合は古い通信を中止して新しいルートで検索し、古い応答を表示しません。各外部検索は6秒、全体には30秒の安全用期限を設けます。見つかったものから表示し、通信失敗・期限切れ・取得上限による未完了を「候補なし」と区別します。一部の候補が得られている場合は、それを残して表示します。

通常はValhallaで検索し、`DistanceExceeded`（距離上限）の応答があった場合はPython側のORS徒歩検索に自動で切り替えます。秋津付近から広島駅の検索では、この距離上限に当たることを確認しています。ORSへの切り替えにはサーバー側の `ORS_API_KEY` が必要です。長距離検索は出発地点と目的地を直接つなぐ徒歩ルートを1本取得し、周辺の見どころ検索は行いません。短距離の従来のルート候補はそのままです。キー未設定・通信失敗・ORS側の検索上限は原因別に表示します。ORSの公開APIにも[距離などの制限](https://giscience.github.io/openrouteservice/hosted-api-restrictions)があるため、すべての距離・地点で取得できる保証はありません。

長距離の確認：Python側にキーを設定して起動し、スタート地点を秋津駅付近、目的地を広島駅にして「徒歩ルートを表示」を押します。開発者ツールのNetworkで、Valhallaの `DistanceExceeded` に続いて `POST /api/walking-routes`（`mode: "standard"`）が1回呼ばれることを確認します。キーを外した場合は長距離検索の設定が必要と表示され、再検索の失敗時も既存の経路は残ります。

目的地の操作欄の「景色を楽しむ」は一時非表示です。処理は保持しており、再開時は `index.html` と `templates/index.html` の `scenic-route-button` から `hidden` 属性を外します。「出発地点に戻る」は表示しています。従来の徒歩ルート・坂道少なめ・自然・コンビニが多い道もそのまま利用できます。取得した候補は色分けして同時に表示し、ルート詳細から比較できます。

- **景色を楽しむ（一時非表示）**：OpenRouteServiceの徒歩ルートで、距離を優先した道と、緑・静かな道を優先する道を比較します。周辺の展望地点や公園内の歩道が見つかれば、そこを経由します。公園の中心や水面を経由地にせず、地図に登録された歩道上の点を使います。
- **出発地点に戻る**：出発地点→指定した目的地→元の出発地点の往復を計算します。見どころがあれば帰りに経由する候補も追加します。帰着地点は最初の出発地点に固定し、GPS更新で変更しません。スタート地点を明示的に変更すると、新しい地点を帰着地点にします。「往復・周回」の距離・時間は帰着までの合計です。

道が限られる場所では往復で同じ道を通る場合があり、完全に別の道で周回できる保証はありません。同じ経路の候補は重複表示しません。所要時間は距離と保存済みの歩行速度から求めた目安で、休憩・滞在・標高差による遅れは含みません。

### ORSの設定

現在のPython側はFlaskではなく標準HTTPサーバーです。既存の構成を維持し、`POST /api/walking-routes` を追加しています。追加のSDKは不要で、既存の `requests` をPython側で使用します。

PowerShellで依存関係を確認し、サーバーを起動する同じターミナルに環境変数を設定してください。

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:ORS_API_KEY = '取得したORSのAPIキー'
.\.venv\Scripts\python.exe app.py
```

Pythonサーバーの `http://127.0.0.1:8000/` または既存のLive Serverから利用します。独自ポートの場合はPythonサーバーからページを開いてください。スマホから利用する場合は、このPython APIへ接続できる同一オリジンのHTTPS配信が必要です。GitHub PagesだけではORS中継APIは動きません。

APIキーは `walking_routes.py` が `ORS_API_KEY` から読み、固定の `api.openrouteservice.org` 宛てのAuthorizationヘッダーにだけ付けます。JavaScript・HTML・JSON応答・URL・ログにはキーを含めません。環境変数はサーバー起動前に設定してください。`.env` 等はGitの除外対象ですが自動読込は行いません。APIキーをREADMEやソースコードへ書き込まないでください。

キー未設定・認証失敗・利用上限・タイムアウト・不正な経路・通信エラーは画面に表示します。追加候補だけに失敗した場合は取得済みの基本経路を返します。再検索時のエラーでも、同じ出発地点・目的地で既に表示している経路は残します。成功したORS候補はサーバーのメモリに5分間保持します。

動作確認：目的地を選び「出発地点に戻る」を押し、最後の道順が「出発地点に戻る」であることを確認します。もう一度押しても帰着地点が変わらないこと、詳細を閉じても線が残ることも確認できます。「徒歩ルートを表示」で従来の案内へ戻れます。「景色を楽しむ」の確認は上記の方法でボタンを再表示してから行い、候補の線・所要時間・道順を比較します。

自動テスト：`.\.venv\Scripts\python.exe -B -m unittest test_walking_routes -v`。外部サービスはテスト用の応答に置き換えるため、実APIキーなしで実行できます。

仕様の参照：[ORSの緑・静かな道の重み付け](https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options)、[経路応答形式](https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/requests-and-return-types)。

目的地を指定し「徒歩ルートを表示」を押すと、まず選んだスタート地点からの基本のルートを表示します。追加の候補は見つかった場合だけ提示し、種類ごとの固定枠・検索中の枠・見つからなかった枠は表示しません。見つかったルートは地図上に色分けして同時に表示し、候補一覧にも対応する色の線を添えます。候補を押すと道順が切り替わり、ほかのルートも表示したままになります。候補が1本だけなら候補一覧も表示せず、そのまま道順を使えます。切り替え時の自動拡大・移動は行いません。

- **基本のルート**：歩行者用の道路・歩道を使うルートです。必ずしも距離が最短になるとは限りません。
- **坂道少なめ**：勾配・階段をなるべく避けて計算し、基本のルートと違う道になる場合に提示します。坂や階段を完全に避ける保証はありません。
- **自然を楽しむ**：公園・自然保護区の歩道を経由できる場合の候補です。私有地・立入禁止・有料指定のある場所を除いて探します。
- **コンビニが多い道**：周辺のコンビニを検索し、最大2か所の店舗付近を経由する候補を比較します。ルートから直線距離で約60m以内にある店舗を数え、基本のルートより件数が多く、2件以上ある候補だけを提示します。同名で約20m以内の重複データはまとめます。件数も画面に表示します。比較した候補の中から選ぶもので、周辺すべての道について件数が最大になることを保証するものではありません。

同じ道を通る候補や、大きく遠回りする候補は追加しません。候補ごとに距離と所要時間を表示します。設定した歩行速度を経路サービスに渡して所要時間を計算します。「道順」を開くと日本語の案内を確認できます。道路名は地図データの表記を使用します。

スタート地点や目的地の切り替えでルートを更新します。「ルートを更新」では選んだスタート地点から計算し直します。現在地を選んでいる場合は最新の位置を取得します。「案内を終了」で線と道順を消します。目的地を解除すると案内も終了します。ルート表示による自動拡大は行いません。

現在地をスタートにして案内中の場合は、表示中のルートを30m以上進んだとき、またはルートから50m以上外れた状態が続いたときに、最新の現在地から自動で再検索します。複数の位置情報で2秒以上確認し、自動更新の間隔は10秒以上空けます。誤差が50mを超える位置や20秒以上古い位置は再検索の判定に使わず、誤差が大きめの場合は逸脱の基準も広げます。更新先のルートをまだ取得できていない間は、次のGPS更新で同じ取得処理をやり直しません。選んでいるルートの種類を優先して取得し、新しいルートが取得できるまでは既存の線と道順を保持します。失敗時も既存の線を残します。追従がオフの場合は地図の表示位置・縮尺を保ち、ルート詳細の開閉状態は追従にかかわらず維持します。検索・地図でスタート地点を固定した場合は、GPSによる自動再検索はしません。

秋津駅の改札内跨線橋は、OpenStreetMapの[通路形状](https://www.openstreetmap.org/way/1252371411)と[西武鉄道の構内案内](https://www.seiburailway.jp/railway/station/akitsu/)を確認して `static/route-access.json` に通行除外範囲を記録しています。駅全体や近くの踏切・一般道は除外しません。Valhallaの[除外ポリゴン](https://valhalla.github.io/valhalla/api/route/api-reference/#other-request-options)を全候補に付け、返された形状も検査します。ORSでも既知の除外範囲を横切る場合だけ[avoid_polygons](https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options#optionsavoid_polygons)を付けて再取得し、回避できなければその候補を表示しません。長距離検索に不要な回避条件を常時付けないことで、既存の距離上限への影響を抑えます。Valhallaの立入制限つき通路への重みも強めていますが、ほかの駅の通行制限は地図データの登録状況に依存します。別の駅も確認できた範囲を同じJSONに追加できます。追加後はPythonを再起動し、ブラウザを再読み込みしてください。

確認方法：秋津駅北側（35.7791, 139.49665）から南側（35.77815, 139.49665）の徒歩検索では、改札内の約179mの経路ではなく駅外側を回る約431mの経路を取得できることを実測しました。案内中に「現在地」を押してもルート取得が増えないこと、追従のオン・オフでカメラだけが変わること、30m程度の進行を2秒以上確認すると10秒以上の間隔で更新すること、近くのコンビニと駅の切り替え・中止・キャッシュが使えることを確認します。自動テストは `node --test test_navigation.cjs test_discovery.cjs` と `.\.venv\Scripts\python.exe -B -m unittest test_walking_routes test_park_search -q` で実行できます。

往復ルートも現在地から更新しますが、帰着地点は元の出発地点に固定します。目的地付近まで進んだことを確認すると、以後は目的地を通り直さず、元の出発地点へ戻る経路を検索します。出発地点付近の最後の30mでは、短すぎるORS再検索をせず最後の経路を表示します。

スマホなど画面が小さい場合は、ルート表示を開始すると目的地・ルート候補・道順の欄を隠し、地図とルートの線を表示します。「ルート詳細」で開き、「詳細を閉じる」で再び隠せます。詳細を隠してもルート案内は終了せず、追加候補が見つかったときやルートの更新後も開閉状態を保持します。詳細を開くと候補を選択でき、道順の確認・ルートの更新・案内終了もできます。詳細の開閉ボタンは内容のスクロール範囲の外に表示します。

- 経路計算には [Valhalla / FOSSGIS](https://valhalla.openstreetmap.de/) の歩行者用モードを利用します。現在地・目的地・経由地の座標と歩行速度を送信します。[歩行者向けの勾配・速度設定](https://valhalla.github.io/valhalla/api/route/api-reference/#pedestrian-costing-options)を利用しています。
- 公園内の歩道・コンビニの検索には [Overpass / Private.coffee](https://overpass.private.coffee/) を使い、現在地と目的地の中間地点・検索範囲を送信します。周辺データは最大10分、ページを開いている間だけキャッシュします。店舗数は取得できた地図データの範囲の目安で、営業時間・店の入口へのアクセス・現地の通行状況は保証しません。
- 経路リクエストは最低1秒間隔です。追加候補の取得に失敗しても基本のルートを使えます。目的地の変更や案内終了時は古いリクエストを中止します。経路を取得できない地点を直線で結ぶことはありません。
- 所要時間は推定です。移動中の現在地は自動で更新します。一定の進行・逸脱時はルートも自動で更新し、「ルートを更新」から手動でも計算し直せます。音声案内はありません。

## 保存と検索

- 記録はブラウザの localStorage に保存されます。端末間の同期はありません。
- 歩行速度も localStorage に保存します。訪問記録とは別のキーを使います。保存できない場合も、その画面を開いている間は選んだ速度で利用できます。
- 同じブラウザ・同じオリジン（プロトコル、ホスト、ポート）で再度開くと、記録を復元します。
- ブラウザのサイトデータを消すと記録も消えます。
- 地図と検索にはインターネット接続が必要です。検索できない場合も地図から手動で登録できます。
- 検索は [Photon](https://github.com/komoot/photon) の公開デモAPIを利用します。虫眼鏡または入力欄での Enter キーで検索します。入力中の自動検索は行わず、日本語変換を確定する Enter キーでは検索しません。結果をセッション内でキャッシュし、連続リクエストは1秒以上間隔を空けます。入力を変えると前の検索を中止し、候補とメッセージを消します。
- 検索候補は最大15件です。国名は国コードから日本語に変換し、住所は現地語で取得して国内の地名を日本語で表示します。現在の公開APIは日本語指定に対応していないため、日本国外の都市名・道路名などは現地語表記が残る場合があります。
- Photon のデモAPIは適度なリクエスト数での利用向けで、稼働保証はありません。多数のユーザーに公開する場合は専用の検索サーバーに変更してください。接続先は `static/js/app.js` の `SEARCH_ENDPOINT` にあります。
- 検索語は検索サービスに送信されます。訪問日・メモ・記録一覧は送信しません。
